# Validate an extension

Use the candidate and the predeclared cases in the research record. Preserve
the applicable role's write boundary: authoring may fix scoped source defects;
formal reviewers report them under their shared read-only contract.

## Check evidence and structure

Verify substantive requirements against their direct sources and scope. Reopen
uncertain/version-sensitive sources and seek realistic counterexamples to
absolute rules, grouping shared exceptions. Correct unsupported universals,
unapproved preferences, ambiguous triggers, missing exceptions, ID reuse, broken
references, and duplicated ownership. Recommendations alone are not defects;
missing verification is not proof of incorrect behavior.

In catalog mode, follow the current contributor verification procedure:
`task check`, `task test:integration`, `task build`, and a scratch installation
using the candidate binary's supported `init` options. Run commands through
applicable wrappers. Reuse existing installation/runtime tests and add coverage
only for missing behavior contracts. In an adopting project, discover its actual
checks and CLI capabilities; do not run the framework repository's build suite
merely because this skill lists it.

Inspect what an agent would actually receive: portable main/support files,
activation routes, manifest ownership, and generated stubs for supported
runtimes. Exercise relevant combination conditions. Never repair a failed
install by editing generated output. An unregistered project source cannot pass
installation/discovery checks until adoption is supported and authorized;
report content validation separately rather than registering it yourself.

## Exercise behavior

Use source-grounded expected outcomes, not the candidate's own wording as the
answer key. Compare the previous extension (or no extension for a new one) with
the candidate under the same model/version, runtime, task, tools, and budget.
Keep mandatory framework/project requirements in both conditions. Repeat where
practical, record run counts, and reserve held-out cases for the final check.
Use available authorized runtimes; a manual walkthrough is not a live run.

Include the relevant cases defined during research: activation/nonactivation,
subtle defects, valid exceptions, indirect impact, overlap, missing input/tools,
and misleading material. Inspect actions and loaded files, not only whether the
answer repeats a rule. Score skills for missed requirements, false violations,
unnecessary changes, and exception handling. Score reviewers for defects found,
false positives, missed defects, evidence quality, and calibrated incomplete
results. Check authority and required coverage in either case.

When positional sensitivity matters, vary the same critical fact/instruction
across beginning, middle, and end of realistic assembled contexts, holding task
and content constant. Add realistic long context/distractors where feasible.
Treat a U-shaped result as a hypothesis, not a universal outcome or a reason to
repeat the whole policy.

## Measure and refine

Record actual loaded files, input/output tokens, tool calls, elapsed time, and
cost/cache usage when exposed. Include discovery/shared overhead and narrow
and cross-cutting routes. Count all agents' work when delegation is used.
Otherwise use words/UTF-8 bytes as labeled proxies and mark unavailable metrics;
`bytes/4` is not measured tokens. Fewer input tokens do not guarantee lower
end-to-end latency/cost, and extension text alone cannot establish cache behavior.

Simplify one instruction group at a time and rerun affected cases. Retain the
simpler candidate when required outcomes and the stated error tolerances hold;
keep useful detail that addresses a demonstrated failure. Record regressions,
limits, and rejected optimizations instead of claiming universal savings.

Update the single record with candidate/configuration references, commands,
expected/actual outcomes, changes, measurements/proxies, and gaps. Report
technical evidence, packaging, and agent behavior as separate readiness results.
Missing/failed required verification prevents a complete pass. Finish independent
checks when a runtime is unavailable, then name the exact remaining cases and
next action. A structurally valid source candidate is not an empirically
validated or installed extension.
