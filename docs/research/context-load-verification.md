Every proposed request budget passes under this normalization. Conditional decisions, recovery, templates,
extensions, mixed interfaces, and canonical changes add their required sources when triggered.

increase available text by 2.8%; the savings come from smaller required loads, not deleting all later procedures.
No stage change unloads earlier context automatically. These results do not measure billing or whole-task savings.

## Structural and behavior checks

- CL-1–3: the request table has one owner; status remains read-only. Shared orchestration contracts route to
  the current stage, and report/correction/PR formats load only before their governed actions.
- CL-4: mandatory rules 1–11 and numbered rules/report/role/skill sections remain addressable. Moved policy
  retains approvals, registration barriers, checkpoint/plan gates, review tiers, candidate stability, and recovery.
- CL-5: existing Go topic routing and extension-authoring stage routing are unchanged. User-only invocation
  metadata remains generated by the CLI.
- CL-6: contracts require recovering necessary context after compaction; recovery continues from durable
  task state and checkpoints. Delegated roles retain standalone preflight and failure gates.
- CL-7–8: route totals include conditional references actually required by each case; unknown runtime usage
  remains unknown. Required missing inputs and failed checks still block dependent work.
- Relative Markdown links/fragments, version stamps, heading/fence structure, and preserved section numbers passed.
- Revised skill frontmatter, names, descriptions, allowed keys, and scaffold checks passed with Ruby's YAML
  parser. The bundled Python skill validator could not run because its optional `PyYAML` dependency is absent;
  no project dependency was added for it.

An independent source walkthrough covered these requests without reading the proposal's expected results:

| Scenario | Observed permitted outcome |
| --- | --- |
| Bare paused task ID | Read task status; no overview, takeover, or resumption. |
| Existing work spec, approved prototype, planning before delegation | Read current-stage/work-spec contracts; prepare the plan; no report or future-stage procedure yet. |
| In-task spec input calls a draft snapshot approved | Read the cited snapshot; block that change and return it through the orchestrator to prototype. |
| Correction would introduce an unapproved dependency | `NEEDS_DECISION`; no dependency change or direct user contact. |
| Reviewer sees dirty worktree and an unrun required check | `INCOMPLETE`; no review/repair, no passing verdict. |

No material lost boundary or missing dependency was found in that walkthrough. It is source-based evidence,
not a live Claude/Codex/Copilot workflow execution.

## Packaging and execution checks

- Existing init/runtime/upgrade/uninstall tests cover installing nested references, generated adapters, Project
  notes preservation, repeatability, ownership, and removal. Fixtures include the 16 additional core files.
- `init` groups only top-level agent files as roles; implementer references are listed as files, preserving six roles.
- Full race-enabled tests with transcripts passed: `GOCACHE=/tmp/go-build INTEGRATION=true go test -race ./...`.
- Static checks passed: `GOCACHE=/tmp/go-build go vet ./...`; configured `golangci-lint run` with caches under `/tmp`.
- Website: `npm run build` and `npm run check` in `site/`; 26 HTML pages passed link/fragment, metadata,
  accessibility-structure, asset, and JavaScript checks.
- Markdown/diff and source-structure checks are scoped to changed files; no implementation commits were created.

Live provider sessions and actual per-call usage were not measured. Packaging checks establish source delivery;
the independent walkthrough establishes the inspected decisions, not every runtime's instruction assembly.
