# Implementation Plan: Uninstall Solomonar from a Project

Status: Proposed. Repository context inspected on 2026-10-24. This document plans the change; it does not make
`uninstall` available or approve new decisions on its own.

## Objective

Add `solomonar uninstall` to remove the framework, installed catalog extensions, and generated runtime adapters
from the selected project checkout. Remove generated active references without deleting project instructions,
extension sources, product documents, or task history. Make the operation reviewable, repeatable, and recoverable
on handled failure.

## Current State

- [go.mod](../../go.mod) declares Go 1.27.3. The implementation needs no new dependency. Existing dependencies
  provide terminal handling and the established testify/testscript test tools.
- [internal/cli/run.go](../../internal/cli/run.go) registers commands using `flag.FlagSet`. `init`, `upgrade`, and
  `extension list|add|remove` exist; no whole-framework removal command exists. Runtime management and guard hooks
  are specified but are not registered or generated by the current build.
- [internal/project/manifest.go](../../internal/project/manifest.go) strictly reads `.solomonar/manifest.json`,
  including version checks and file ownership. The manifest tracks installed paths and base hashes; it does not
  record the original contents of a pre-existing `AGENTS.md`.
- [classify.go](../../internal/project/classify.go) already plans removals and resolves edited files with
  `--keep` or `--overwrite`. Its generic removal logic compares a whole file's hash, which is unsuitable for
  `AGENTS.md`: only the prefix above `## Project notes` is managed and hashed.
- [apply.go](../../internal/project/apply.go) applies file changes through `os.Root` and journals content,
  permissions, and directory changes for rollback. Its empty-parent cleanup deliberately preserves top-level
  directories, `docs/solomonar`, and the extension-store root.
- [core.go](../../internal/project/core.go), [runtime.go](../../internal/project/runtime.go), and
  [store.go](../../internal/project/store.go) establish the installed artifacts. Catalog extensions are managed;
  project extensions share `docs/solomonar/extensions/` but their sources are project-owned.
- [interface.md](interface.md) owns behavioral contracts and `CLI-D-*` decisions;
  [architecture.md](architecture.md) owns structure and `AD-*` decisions. The interface currently says the core
  cannot be removed. That wording needs an explicit whole-framework uninstall exception.
- [site/README.md](../../site/README.md) assigns command syntax and examples to the site command pages and marks
  `docs/design/` as historical. Those historical notes must remain unchanged.

## Scope

**Confirmed requirements:** plan one new removal command, including framework references and extensions, and
include changes to the current design, decision records, and documentation website. This change writes only this
implementation plan; implementation and the other documentation changes are future tasks.

**Conservative assumptions used by this plan:**

1. Uninstall means removing the project installation. Removing the executable, Homebrew package, runtime
   applications, or user-wide configuration is separate.
2. Task history and authored project content survive uninstall. A project extension is deactivated by removing
   its generated registrations; its source directory survives.
3. The operation affects the checkout selected by the working directory or `-C`, including a linked worktree.
   It does not edit other worktrees, branches, or remotes. No clean-worktree or main-branch restriction is added.
4. Automatic reference cleanup is limited to managed instructions/adapters and the exact generated framework
   index entry in `docs/README.md`. Historical references and customized prose are preserved.

**In scope:** ownership-based removal, notes preservation, explicit conflict resolution, dry runs, confirmation,
human/JSON output, rollback, supported older manifests, and documentation of retained content.

**Out of scope:** registry/ref deletion, task cancellation, worktree or branch removal, commits or pushes,
recursive directory deletion, arbitrary repository-wide text replacement, binary self-removal, purge/force modes,
new configuration, and implementation of the deferred runtime or guard commands.

**Dependencies:** existing Git discovery, strict manifest decoding, project plans/journal, and CLI output/prompt
helpers. No registry migration, extension validation, runtime executable, authentication, or network is required.

## Architectural Decisions

Keep AD-1 through AD-15 and CLI-D27's ownership boundary. Record the following as proposed additions in the
existing decision tables, using the next free IDs when implementation starts; do not create another decision system.

| Decision to record | Proposed choice and consequence |
| --- | --- |
| Whole installation boundary | One top-level `uninstall`; no `remove` alias or selective core removal. Qualify “core cannot be removed” as applying while the framework remains installed and to `extension remove`. |
| Ownership and history | Use recorded ownership and hashes rather than regenerating today's asset list. Preserve project extension sources, seeded documents, decision entries, and `workflow-state`. Uninstall writes no “stack selection: none” decisions because installed technology is unchanged. |
| Shared instructions | Remove only the verified managed prefix of `AGENTS.md`; preserve the notes suffix byte-for-byte, including adopted instructions and its heading. Original pre-install formatting cannot be reconstructed. |
| Seed reference exception | Permit uninstall to remove only the exact generated framework index line from the seeded `docs/README.md`; retain all other bytes. This is an explicit, narrow amendment to the current “seed: never modified” contract. |
| Existing execution boundaries | `internal/project` computes a concrete removal plan; `internal/cli` handles discovery, flags, confirmation, output, and execution. Reuse `Plan`, `Resolutions`, `Apply`, and `Journal`; add no package, interface, dependency, or manifest schema. |

### File handling contract

| Artifact | Uninstall behavior |
| --- | --- |
| Hashed `core`, catalog `ext:<name>`, and whole-file `runtime:<name>` records | Remove regular files whose current hash equals the recorded base. Missing files need no action. Edited files conflict. Include legacy tracked locations, such as `docs/solomonar/skills/go/`; do not require an upgrade first. |
| `AGENTS.md` with `core+notes` | Verify the managed prefix using the existing notes boundary and recorded hash. If verified, write back the exact notes suffix when it contains project content. Remove the file only when no notes exist or the suffix contains only whitespace and the exact generated heading/comment. A changed prefix or missing boundary that prevents verification conflicts. |
| Edited managed files | Unresolved conflict prevents every write. `--keep <path>` preserves the entire file and reports it as left unmanaged; `--overwrite <path>` authorizes removal. For `AGENTS.md`, overwrite removes the managed prefix while preserving a recognizable notes suffix. Never discard notes to resolve a missing/ambiguous boundary; require keeping the file or restoring the boundary manually. |
| Project extensions, including inactive/draft sources and legacy `project-ext:<name>` records | Preserve all source bytes and extra files, even when an old manifest hashes them. Remove only their managed runtime registrations and framework instruction entries. Do not load or validate `extension.json` to uninstall. |
| `docs/README.md` | When present as a regular project file, remove only the exact standalone line shown below from its `## Documents` section. Preserve the rest, including line endings. Do not create a missing README. Leave customized entries unchanged and report known remaining framework references in that file for manual review. |
| Decision, stack, architecture, specification, work, report, prototype, and other seeded/authored documents | Preserve. Existing decisions and historical links are evidence, including decisions that reference removed extension paths. |
| `CLAUDE.md` | Remove only when recorded as a managed whole file and unmodified, or explicitly resolved as above. An existing untracked file remains unchanged. If a retained file imports a removed `AGENTS.md`, report the dangling import for manual review. |
| Other runtime configuration and hooks | Preserve untracked files and unrelated configuration. The current build installs no hook entries. If a manifest contains an entry-only runtime record, report an unresolved `file_conflict` before writes; do not delete its containing JSON file or silently drop tracking. Entry removal must be added alongside the future hook implementation. |
| `.solomonar/manifest.json` | Remove last among file changes after all conflicts resolve. Do not regenerate an empty manifest. A missing manifest means no automatic cleanup can be inferred. |
| Empty directories | Reuse normal removal cleanup. Additionally allow uninstall to prune `docs/solomonar/extensions`, `docs/solomonar`, and `.solomonar` only when empty, through the journal. Preserve nonempty directories and the shared top-level `docs`, `.claude`, `.codex`, `.agents`, and `.github` directories. |
| Registry and Git metadata | Preserve `refs/heads/workflow-state`, any remote counterpart, task branches, worktrees, `.git`, and `.jj`; do not read registry records or write refs. |

The generated index line is:

```text
- `docs/solomonar/`: framework rules, roles, and skills
```

Deletion authority is limited to the ownership locations above, including supported legacy locations. Reject a
managed record targeting unrelated source files or Git metadata as a conflict; `--overwrite` cannot authorize
such a path. Project extension source preservation takes precedence over a legacy hash record.

Confined I/O does not make symlinks safe deletion targets. A target replaced by a symlink, directory, or special
file conflicts; overwrite must not follow or recursively remove it. Do not traverse symlinked parent directories,
including links to another location inside the checkout. Preserve unsafe targets with `--keep` when supported by
the existing removal rules. For shared instruction/index files, refuse unsafe access without rewriting them.

Use the existing handled-failure rollback contract. Before applying an accepted plan, check that its manifest
and affected file contents/types still match what was planned; a change during confirmation must require a fresh
plan rather than silently widening deletion. This does not introduce cross-process locking or promise recovery
after SIGKILL, power loss, or simultaneous filesystem writes during apply.

## CLI Behavior

### Syntax and flags

```text
solomonar uninstall [--keep <path>]... [--overwrite <path>]... [-y|--yes] [--dry-run] [--json]
```

```sh
solomonar uninstall --dry-run
solomonar -C /work/ledger uninstall --yes
solomonar uninstall --keep docs/solomonar/rules.md --yes
solomonar uninstall --overwrite .claude/skills/solomonar/SKILL.md --yes --json
```

- No positional arguments. Global `-C`, `-v`/`--verbose`, and `--no-color` behave as today.
- Repeatable conflict flags accept exact repository-relative paths, following existing validation: a path in
  both lists, an unsafe path, or a path that is not a resolvable conflict is `invalid_value` (exit 2). Repeating
  the same path has no additional effect. `--yes` never resolves conflicts.
- Without a manifest, return exit 0 without prompting: `No Solomonar manifest; nothing to uninstall automatically.`
  Do not search for guessed installation files. Conflict flags still require actual conflicts and therefore reject.
- Accept older framework versions that the strict decoder supports, including the v0.1.7 layout. Reject newer
  manifest/framework versions with `cli_outdated`; malformed manifests retain `manifest_invalid`.
- No new environment variables. `NO_COLOR` retains its global meaning; `SOLOMONAR_OWNER` is irrelevant here.

### Streams, confirmation, and results

- Follow `confirmed`: when stdin/stdout are terminals, show the plan on stderr and use the existing
  `Proceed? [Y/n]` confirmation. Declining returns exit 0 and `Cancelled; nothing was written.` on stdout.
- A writing invocation without a terminal, or with `--json`, requires `--yes`; otherwise return
  `interactive_required` (exit 2). `--dry-run` and the absent-manifest no-op never prompt or require `--yes`.
- `--dry-run` runs the same validation and conflict checks, prints the complete plan and
  `Would uninstall solomonar from <root>` on stdout, and changes no files, directories, or refs.
- On success print `Uninstalled solomonar from <root>`, existing action counts, retained project content, and a
  concise `Next:` instruction to review and commit the changes. Do not stage, commit, push, or recommend staging
  unrelated paths. State that the registry and other worktrees remain unchanged.
- Conflict output follows existing project commands: the human file plan goes to stdout; actionable
  `check`/`found`/`fix` diagnostics go to stderr. Warnings identify retained managed files and known manual
  reference cleanup; historical references are expected and need no warning.
- JSON uses the existing envelope with `command: "uninstall"`. Success data contains `project`, `files` using
  existing path/action/owner/reason entries, `preserved` paths/refs, and `next`; include `dry_run` or
  `already_absent` when true. Keep arrays stable and sorted where order is not operational. Failures use the
  existing error envelope without success data; warnings stay in the envelope, with no human prompts or plans.
- A second successful invocation is the absent-manifest no-op. Explicitly kept files and user references may
  remain; the success message must not claim every occurrence of “Solomonar” has been erased.

### Failures and side effects

| Exit | Condition |
| --- | --- |
| 0 | Successful removal, dry run, absent-manifest no-op, or declined confirmation. |
| 1 | `manifest_invalid`, unsupported Git version, unexpected I/O/Git failure, or failed apply. Roll back handled partial changes; surface rollback errors without claiming restoration succeeded. |
| 2 | `invalid_usage`, `invalid_value`, or `interactive_required`. |
| 3 | `not_a_repository` or `cli_outdated`. |
| 4 | `file_conflict`, including edited/unsafe managed files, unsupported entry removal, or changed plan inputs. |
| 130 / 143 | SIGINT / SIGTERM before successful completion, using the existing interruption mapping and rollback. |

Only the selected checkout's planned files and empty owned directories change. No network calls, registry
updates, task-state transitions, or external application changes occur. Preserve current commit-point semantics:
once all changes have completed successfully, report success rather than invite a destructive retry. Review the
existing unconditional `nothing was written` error footer if a rollback fails; that exceptional case must identify
the paths needing recovery instead of making a false guarantee.

### TASK-02: Plan ownership-based removal without writing files

**Objective**

**Dependencies**

**Scope**

**Relevant code**

**Acceptance criteria**

## Final Verification

Implementation completion requires:

- Focused task checks pass; `task check`, `task test:integration`, and `go vet ./...` pass on the supported Go
  toolchain. Run the site build/check from `site/` after the final documentation changes.
- In disposable repositories, compare filesystem snapshots, modes, and registry tips across dry-run, rejection,
  cancellation, handled failure, success, rerun, and clean reinstall. Confirm explicit keeps and authored content
  survive. Verify an uninstall in one linked worktree leaves the others unchanged.
- Review scope: no added production dependency, manifest schema, generic abstraction, remote mutation, or
  unrelated change to init/upgrade/extension behavior. Preserve their existing regression tests.
- Confirm current design/decisions and public command documentation describe the tested behavior. Document any
  unresolved verification limit; do not treat a planned check as a passing result.

Only repository inspection and review of this plan occur during planning. No implementation tests or CLI
uninstall runs have been performed for this feature.

## Open Questions

None block this plan under the stated conservative assumptions. Removing project extension sources, deleting
the registry, uninstalling the executable, or rewriting arbitrary project prose would expand the scope and need
a separate explicit decision. Future guard-hook delivery must include removal of only its own configuration
entries; it must not rely on whole-file deletion by this command.
